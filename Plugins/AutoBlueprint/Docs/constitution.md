# AutoBlueprint 编码规范 Constitution

版本：1.1 草案；日期：2026-10-30；适用基线：ProjectOne、Unreal Engine 5.3.2、UnLua 2.3.6、Win64 Editor。

本文约束 AutoBlueprint 项目插件及其 Lua 工具脚本、C++ 桥接、布局协议、测试和示例。遵循 UE 编码规范，并为后续控件/API 扩展保留清晰入口；脚本层采用项目已有 UnLua，资产构建核心位于 C++ Editor 模块。

“必须”表示实现和代码评审的约束；“应”表示默认采用、确有理由时可调整并记录原因；“可”表示可选方案。已明确确认的需求优先于本规范中的建议。列举未来扩展点不代表把这些功能加入首版。

## 1 适用范围与首版边界

- 插件代码必须放在 `ProjectOne/Plugins/AutoBlueprint/`。依赖 UE 自带插件通过描述文件和项目配置声明；不得以复制代码到 Engine 或修改引擎源码作为本插件的正常安装步骤。
- 首版生成范围是原生 `UUserWidget` 的控件树、布局、贴图、样式和变量。Lua/UnLua 用作编辑器生成入口；按钮等业务事件的 UnLua 绑定、动画和 Event Graph 自动生成属于后续能力。
- 首版目标资产采用 `CreateOnly`：同名资产已存在就报告冲突。覆盖重建和保留人工修改的增量更新是后续独立能力。
- 本规范适用于新增和实质修改的自有代码。不得为统一风格而大规模改写 UnLua 等第三方代码或无关历史文件。
- 实现以 UE 5.3.2 可用 API 为准；其他 UE 版本和平台的兼容性必须通过实际验证后再声明。

## 2 遵循 UE 编码和命名规范

以 Epic 官方 [Unreal Engine C++ Coding Standard](https://dev.epicgames.com/documentation/en-us/unreal-engine/epic-cplusplus-coding-standard-for-unreal-engine?application_version=5.3) 及目标版本的反射、模块规范为基准。下表是本项目常用约定，不替代完整的官方标准。

| 对象 | 规则与示例 |
| --- | --- |
| UObject 派生类 | `U` 前缀，例如 `UAutoBlueprintSubsystem` |
| Actor 派生类 | `A` 前缀；只有实际继承 Actor 时使用 |
| 结构体和通常的非 UObject 类型 | `F` 前缀，例如 `FAutoBlueprintBuildResult` |
| 枚举类型 | `E` 前缀，优先 `enum class`；例如 `EAutoBlueprintWritePolicy::CreateOnly` |
| UE 接口与 Slate 控件 | 按实际类型使用 `I`、`UINTERFACE` 的 `U` 包装类、`S` 前缀 |
| 模板类型 | 按 UE 约定使用 `T` 前缀 |
| C++ 函数和普通变量 | PascalCase，例如 `ValidateLayout`、`WidgetName` |
| C++ 布尔变量 | `b` 前缀，例如 `bSave`、`bIsValid` |
| 宏 | 大写下划线命名；不要用宏代替正常函数或常量 |
| Lua 局部变量和辅助函数 | `lowerCamelCase`，如 `layoutPath`、`printDiagnostics`；模块文件使用稳定名称 |
| Lua 调用 UE 反射 API | 保留实际 C++ 类型、函数与字段名，如 `BuildFromLayoutFile`、`bSave` |
| JSON 字段 | `lower_snake_case`，例如 `schema_version`、`is_variable` |
| 生成控件名称 | 稳定且有语义，例如 `RootCanvas`、`IMG_Product`、`BTN_Confirm`、`TXT_Total` |

- C++ 使用 UE 的大括号与制表符缩进风格；新增 Lua 工具脚本使用四空格缩进、局部变量及模块返回表，避免隐式全局变量。调用静态函数用 `.`、实例方法按实际绑定使用 `:`；维护既有代码时保留其风格。
- 源文件使用 UTF-8。新 C++ 文件沿用仓库的 CRLF 约定；其他文件保留相应语言和目录的现有换行格式，避免整文件换行变更。
- 头文件使用 `#pragma once`。含反射声明的头文件必须把对应 `.generated.h` 放在最后一个 include。
- 遵循 IWYU，显式包含所需声明；`.cpp` 优先包含对应头文件。不得依赖偶然的传递 include、Unity Build 或预编译头掩盖缺失依赖。
- API 使用清晰的动词和业务名词；避免 `Manager2`、`DoStuff` 等含义不明的名称。类只承担明确职责，内部状态默认私有。
- 使用 const correctness；只读的大对象参数优先使用合适的 const 引用。需要固定宽度、序列化或跨平台约定时使用 `int32`、`uint32` 等 UE 类型。
- UObject、反射、容器和字符串优先采用适合 UE 的类型和机制。新增 `UCLASS`、`USTRUCT`、`UFUNCTION`、`UPROPERTY` 必须有反射、GC 或脚本调用的实际用途，不为所有内部类型都添加反射。
- Public 头文件只暴露调用方需要的契约；实现细节放 Private。`Build.cs` 的 Public/Private 依赖必须与实际头文件暴露关系一致。
- 注释解释约束、原因、生命周期和失败行为，避免复述代码。对外 API 必须说明输入、返回值、是否修改/保存资产、运行线程和适用阶段。

Lua 通过 UnLua 调用真实的 UE 反射接口，例如 `UE.UAutoBlueprintLibrary.BuildFromLayoutFile(...)`，字段使用 `options.bSave`。这些自定义接口需在实现和桥接测试后才能标为可用；内部 Lua 辅助函数的命名不改变 UE 的反射名称。

## 3 控件扩展必须有稳定入口

控件支持应通过类型注册表与适配器或处理器接入。可以从简单的静态类型表开始，不要求首版实现动态插件发现或复杂的扩展框架。

每种受支持控件必须在统一位置声明：类型标识、UE 类、可用属性、子节点策略、Slot 规则、资源需求及校验处理。解析、预检、资源解析、构建、编译、保存的主流程负责调度；不得在多个模块里重复散布随控件数量增长的类型判断。

新增一个控件的常规路径应是增加或扩展其注册描述、构建/属性/Slot 处理，以及对应示例和测试。除非它引入新的行为类别，否则不应要求重写主流程或破坏已有配置和 API。

| 行为类别 | 示例 | 必须遵循的规则 |
| --- | --- | --- |
| 叶子控件 | Image、TextBlock、Spacer | 不接受布局子控件 |
| 单子节点容器 | Button、Border、SizeBox、ScaleBox | 最多一个直接子节点 |
| 多子节点面板 | CanvasPanel、Overlay、VerticalBox、未来的 ScrollBox | 通过父容器添加子节点，设置父容器实际产生的 Slot |
| 数据驱动和虚拟化控件 | 未来的 ListView、TileView、TreeView | 数据项、Entry 类和条目生命周期走专门的策略，不按普通面板逐项 AddChild |

- 必须由父控件决定子控件的 Slot 类型。CanvasPanel 的坐标、锚点不能直接套给 VerticalBox 或 ScrollBox。
- 后续支持 ScrollBox 时，必须处理 `UScrollBoxSlot` 及滚动方向、Padding、Alignment 等能力；不能仅把类名加入创建列表就称为支持。
- 后续支持 ListView 时，必须明确数据项对象类型、Entry Widget Class、`IUserObjectListEntry` 契约、条目复用和刷新规则。列表数据项不能伪装成控件树中固定存在的子控件。
- ListView 的设计预览、运行时数据供给和交互属于不同能力，必须分别说明支持程度。不能用若干静态行的预览代替真正的列表支持。
- 允许不同类型复用属性或 Slot 处理器，无须机械地为每个控件建立一个新类。新增抽象必须解决可指出的变化点；不要提前实现尚未需要的通用属性编辑器或业务系统。
- 未实现的控件必须返回明确的不支持诊断，禁止静默替换为其他控件。

## 4 API 和 Schema 必须可以演进

- Lua 对外入口围绕校验、构建和结果处理等稳定操作设计；C++ 静态门面转调编辑器子系统，不复制核心逻辑。文件读取与最终校验由 C++ 统一完成，内部使用类型化布局描述。
- 同一协议版本的布局配置共用一套 Schema；每个界面只提供自己的布局 JSON。不同控件可以有不同的类型约束，不为每个界面复制一份独立 Schema。
- `schema_version` 表示布局协议版本；插件版本、UE 版本和业务界面版本必须分别管理。
- 新增可选字段必须给出清晰默认值，并保持已有配置的行为；删除字段、改变单位/语义、改变必填项等破坏性修改必须显式进行协议版本处理，并提供迁移说明或明确的拒绝信息。
- 旧插件遇到未知控件、字段、枚举或协议版本时必须明确报错，不假装已支持新能力。JSON Schema 的基础检查不能代替 C++ 的 UE 类型和资源检查。
- C++、Lua API 与 JSON Schema 必须保持一致；Lua 使用实际反射字段名，JSON 与报告使用其约定字段。变更时同步默认值、示例、能力说明和测试，不能把尚未实现的接口标为可用。
- 对外 API 使用参数结构组织可扩展选项，避免不断增加位置参数。不要依赖参数顺序隐含行为，也不要提供能绕开验证的任意 UObject 属性写入入口。
- 控件名称必须在相应生成资产中唯一、稳定，并显式指定 `is_variable`。不要依赖项目的自动变量创建设置。
- 布局坐标、边距、锚点、颜色空间、字体单位和默认值必须在协议中说明；设计尺寸、运行时 DPI 和实际视口是不同概念。

配置输入格式示意如下；完整字段与类型以对应协议版本为准。

```json
{
  "schema_version": 1,
  "asset": {
    "package_path": "/Game/UI/Cashier/WBP_CashierMain"
  },
  "design": {
    "width": 1080,
    "height": 1920
  }
}
```

## 5 编辑器工具与运行时必须隔离

- 资产生成、蓝图编译和保存代码放在 `Editor` 模块中。Lua 通过 UnLua 在 UE 编辑器进程内调用 C++；AutoBlueprint 的插件依赖声明 UnLua，Lua 宿主相关实现留在 Private，不向调用方暴露 lua_State 或私有实现。
- 首版生成蓝图只能依赖原生 UMG 和合法的运行时资源，不得继承、引用或持有 `AutoBlueprintEditor` 内定义的类和对象作为运行时内容。
- 未来 ListView 所需的数据对象、Entry Widget 或自定义控件如涉及新增运行时代码，应单独设计项目 Runtime 或插件 Runtime 模块，并声明依赖；不得把它们放进 Editor 模块后直接写入生成资产。
- 复用 UnLua 的脚本与反射能力，但生成工具不得依赖游戏 BeginPlay、默认 Lua 启动模块或收银业务状态。业务事件的 UnLua 接入仍是后续独立能力，不与编辑器脚本宿主混为一谈。
- 实现和测试应使用 UE 公共 API。不得通过引用 Engine 私有头文件目录规避模块边界；确实存在公开 API 缺口时，应记录限制并调整设计。

- 编辑器工具必须管理独立的 UnLua 环境和明确的任务生命周期，无需启动 Play；不借全局启停游戏 Lua 环境执行工具任务。PIE/SIE 期间拒绝资产写入，并提供明确诊断。

- Lua 工具源码放在插件 `Scripts/Lua/` 等编辑器工具目录，使用受控的模块加载路径；不得因为放入已配置随游戏分发的 `Content/Script/` 而被意外打包。环境、Lua 引用和回调在任务结束或适当关闭阶段清理。

## 6 资产写入必须可预期

- 校验 API 不得创建、导入、修改或保存资产。构建 API 在执行写入前必须重新核验配置、目标冲突和依赖，不能只信任此前的预检结果。
- 首版严格采用 `CreateOnly`。目标 Widget 资产已存在，包括磁盘资产或已加载的同名包/对象时，必须报告冲突；不得自动删除、改名替换、覆盖或把更新伪装成“修复”。
- 首版布局调整通过明确指定新资产名生成。旧蓝图中的手工控件、事件、动画和绑定不会被自动迁移到新资产。
- 源图片文件路径、UE 包名和对象路径必须分别建模；通过 UE 路径和资产 API 校验，不能把文件路径直接当对象路径，也不能手写 `.uasset` 二进制。
- 源文件和目标资产路径必须规范化并检查允许的目录边界。首版生成范围为项目 `Content/UI` 和 `/Game/UI`；不能让路径拼接越出目标范围。
- 已有资源复用、源图导入和重新导入必须是明确不同的操作。默认不覆盖已有纹理，也不修改其他界面可能共用的纹理压缩、分组和采样设置。
- 导入前检查源文件存在、类型可读及 Git LFS 内容已实际下载。不能把 LFS 指针文本当作图片导入。
- 蓝图编译失败时不得保存失败的目标 Widget。保存时逐包检查结果，并报告已保存、未保存和部分失败的资产，不能只返回一个模糊的布尔值。
- 编辑器事务和撤销不等于跨文件原子保存。不得承诺多包写入自动回滚，也不得在失败清理中删除用户原有资产。
- 覆盖重建、人工修改检测和增量更新必须作为后续独立设计处理。配置或控件树 hash 仅能反映对应内容，不能据此证明事件图、动画和绑定没有被修改。

## 7 UObject 生命周期与执行约束

- UObject 创建、控件树修改、资产导入、编译和保存必须在适用的编辑器主线程上下文执行。Lua 协程本身不创建后台线程，恢复执行时仍须满足主线程与有效执行阶段的要求；不得从 C++ 工作线程执行未经验证的 UObject 操作，也不得并发访问同一 Lua 环境。
- 控件必须由正确的 WidgetTree 构造和持有，设置唯一根节点并保持合法父子关系；不能把预览实例上的临时改动误当作 Blueprint 资产模板的持久化修改。
- 跨阶段保留 UObject 引用时，必须使用与所有权相符且 GC 可追踪的机制，例如在 UObject 中使用 `UPROPERTY()` 标注的 `TObjectPtr<T>` 成员；原生持有者则使用适当的 GC 引用收集或强引用机制。单独声明 `TObjectPtr` 不等于该成员已经被 GC 跟踪。非持有引用可使用 `TWeakObjectPtr` 并检查有效性。
- 不得以普通裸指针、未被 GC 跟踪的容器或 Outer 关系代替必要的强引用管理。不要用普通 `TSharedPtr` 管理 UObject，也不要以长期 `AddToRoot` 掩盖生命周期问题。
- 创建对象、资源引用、预览实例和编译重实例化的生命周期必须明确。模块注册的委托、回调和扩展入口应在适当的关闭阶段解除。
- 不引入隐藏的全局可变状态；缓存需要明确所有者和失效条件。一个生成任务失败不应污染后续任务。

## 8 错误报告和能力说明

- 用户输入、缺资源、同名冲突和不支持控件等预期错误必须通过结构化诊断返回；不得用 `check`、崩溃或 C++ 异常处理正常的输入错误。
- 诊断至少提供严重程度、稳定错误码、JSON 路径、相关控件/资产名和可理解的信息。调用者依据错误码判断，不依赖解析一段日志文本。
- 必须区分“校验通过”“构建完成”“编译成功”“保存成功”。配置要求保存时，只有必要包全部保存成功才可宣称生成并保存成功。
- 日志使用专用 UE 日志类别，例如 `LogAutoBlueprint`，按 Log/Warning/Error 分级；Lua 封装必须传播失败，宿主需收集 Lua 异常、脚本位置和调用栈，不吞掉错误或仅打印成功。
- 维护每种控件的能力说明，包括支持的属性、Slot、资源类型和限制。新增类型、支持更多属性或改变默认值时同步更新。
- 例如原生 Button 的 `FButtonStyle` 没有独立 Focused 画刷；首版请求自定义焦点贴图时应明确诊断，不能静默忽略后仍宣称五态均已实现。

## 9 验证必须覆盖实际资产行为

- 验证力度与变更风险匹配。对纯文档或低影响可逆调整做相应检查即可，不为凑覆盖率编写复述实现的测试。
- 修改解析、校验、控件或 Slot 行为时，应覆盖有效配置、无效输入和相关边界条件。错误必须可定位到对应配置。
- 新增控件支持必须至少验证：正确构建、非法父子/Slot 被拒绝、关键属性和资源保存后可恢复，以及重新打开资产后仍可正常实例化。
- 涉及 CreateOnly、导入冲突和保存失败的修改，必须验证不改变已有资产，并检查部分结果报告是否真实。
- 未来支持 ListView 时，还需验证数据项更新、Entry 复用和刷新；静态树快照不能替代这些测试。
- 结构测试、编译测试、运行时实例化和视觉验收分别报告。视觉比较必须说明视口尺寸、DPI、字体和贴图条件；无渲染命令行运行不能用于宣称截图一致。
- 不以 `.uasset` 字节完全相同作为可重复性标准；比较控件结构、稳定名称、受支持属性、资源引用和编译结果。
- 涉及模块边界或运行时依赖时，检查生成资产的 Editor 类型引用，并完成相关 cook/打包验证。
- 只有在 UE 5.3.2 中实际编译、生成、保存和重新加载后，才能宣称该链路可用。缺少 UE 环境时应明确列出已完成检查与尚未验证项，不能用静态检查代替运行结果。

- Lua 入口必须验证无需 Play 即可调用 C++、创建并保存蓝图，且新会话重开后仍可用；另验证连续任务、脚本异常、环境释放和与游戏 Lua 的隔离。仅确认 UnLua 能打印日志不等于资产生成链路通过。

## 10 可维护性和变更交付

- 每个模块职责单一；资源解析、控件构建、属性/Slot 映射、编译保存和诊断应分层，避免一个函数同时承担所有工作。
- 一次生成任务内应复用已解析的资源引用，避免为每个控件重复扫描 Content 或重复加载同一纹理。性能优化基于实际规模和测量，不提前引入异步和复杂缓存。
- 对配置的节点数、深度等资源消耗设置明确、可诊断的边界；配置中的子节点顺序和布局层级应保持确定性。
- 布局 JSON 只描述数据，不执行其中提供的任意脚本或表达式。用户明确运行的 Lua 工具脚本由编辑器入口加载，通过受校验的 C++ API 执行生成；两类输入的职责必须分开。
- 变更只覆盖当前任务需要的范围。公共接口或布局协议发生变化时，说明行为变化、兼容性、默认值及迁移方式。
- 提交或交付说明应包括改了什么、为什么、验证结果和实质限制。原始 `.uasset` 与图片按已有 Git LFS 规则管理；构建产物遵循 `.gitignore`。
- 扩展性规范用于降低后续修改成本，不要求首版提前实现 ListView、ScrollBox、运行时模块或尚未确认的业务逻辑。
- 本规范修订时更新版本与修订记录，并同步相关实现和文档；日常在授权范围内的实现选择无需因本文件新增重复确认流程。
